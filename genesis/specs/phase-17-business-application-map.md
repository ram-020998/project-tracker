> **Goal:** Turn the internalized Appian knowledge base (Phase 16) into **business understanding**. Produce **one clean,
> high-level, business-language picture of what an application *does for the business*, end to end** — combining **(A) the
> end-to-end business value stream(s)** and **(B) the business-capability constellation** — generated by an **agent** that
> reads the KB as ground truth, and rendered in the web UI. This is **not** a technical map: no objects, bundles, pages,
> interfaces, record types, or properties appear anywhere in the output; those terms are banned from the business vocabulary.
> **Repos:** **genesis** (migration **m0008** `kb_business_maps`, `KbStore` business-map read/write + evidence-pack
> extractor, the Applications **Business Map** API + web view) + **genesis-workflows** (the new deterministic
> **`generate-business-map`** LangGraph workflow + catalog entry). **genesis-core** likely unchanged.

> the code-free KB. To be trustworthy it is **evidence-grounded**: every business element (capability, entity, stage,
> actor) must cite the real KB objects it was inferred from, and program **validators enforce referential integrity +
> coverage + a business-language guard** so nothing is hallucinated (ADR-011). LangGraph owns control flow; agent steps
> only *interpret* (ADR-001). The map is **code-free** (ADR-037), **point-in-time** (generated from a specific sync,
> persisted, regenerated on demand — ADR-030/032), and **read-only against Appian** (KB-only; no environment round-trip).

## 0. TL;DR

Phase 16 gave Genesis a **technical** knowledge base (objects, dependencies, entry-point bundles, process flows — all
code-free). That is exactly what agents and MCP tools need, but it is **not** what a human wants when they ask *"what does
this application actually do for the business?"* Phase 17 answers that question with a single, clean, **business-language**
diagram — the **Business Application Map** — synthesized by an agent from the KB and rendered in the web.

1. **A derived "Business Model" artifact.** A new **agent-driven, deterministic LangGraph workflow** (`generate-business-map`)
   reads the KB (via the read-only `genesis-kb` MCP + `KbStore`) and produces a compact, structured **`BusinessModel`** (a
   versioned JSON contract — see `phase-17-business-application-map/business-model-contract.md`) describing the app purely in
   business terms: a one-paragraph **summary**, the business **domain**, the core business **entities**, the business
   **capabilities** (functional areas) and how they hand off, the **actors**, and the end-to-end **value stream(s)** (ordered
   business stages with decision branches).
2. **Two coordinated views, one picture.**
   - **(A) Value stream** — the app's primary business journey(s) as a left-to-right flow of **business stages** (e.g.
     *Intake → Classify → Review → Approve/Reject → Archive → Report*) with decision branches, and the entity/actor at each
     stage. This is "the complete business flow of the application."
   - **(B) Capability constellation** — the app's functional areas as a small set of clustered **capabilities** around the
     business **domain**, the core **entities**, and the hand-offs between capabilities. This is the one-glance "what is this
     app about" overview.
   The two are **linked** (focus+context): selecting a capability highlights its stages in the value stream and vice-versa.
3. **Evidence-grounded, not hallucinated.** Every business element carries hidden **evidence** (the KB object UUIDs it was
   inferred from). Program **validators** reject any element that references objects not in the KB, enforce a minimum
   **coverage** of the app, and enforce a **business-language guard** (banned technical tokens). Failing agent output is
   retried, then escalated to a **human review gate** (ADR-011/021). The result is a business map you can trust.
4. **Persisted + point-in-time.** The model is generated from a specific **sync** (`source_sync_id`) and persisted in
   `genesis.db` (migration **m0008**, `kb_business_maps`), so it is instant to view, shows *"based on sync #N / generated
   {when} / {credits} credits / {coverage}% covered"*, and is **regenerated on demand**. A later sync marks the map **stale**
   (the UI prompts a regenerate). Release snapshots are schema-ready for later (mirrors the Phase-16 `kb_bundles`/release
   pattern).
5. **Business-only, code-free, read-only.** The output uses business language exclusively; it stores no SAIL (ADR-037); it
   reads only the local KB (no environment round-trip → fast, offline, deterministic inputs). A *technical* graph is a
   **separate, later** effort and explicitly out of scope here.

The heavy intermediate data (the evidence pack, each agent step's output) lives in the run **blackboard** (ADR-010/018); only
the compact final `BusinessModel` reaches `kb_business_maps` and only pointers reach LangGraph state.

## 1. Motivation & user story

> *"We've done the hard integration work — we can add an Appian application, parse it, and store its knowledge base inside
> Genesis. Now it's time to get **value** out of that data and help people **understand** the application. I don't want the
> actual sites, pages, reports, objects, or bundles shown, and I don't want to click an object and look at its properties —
> that's information I can get straight from the environment; we're not rebuilding the environment in a UI. What I want is a
> **business diagram**: from a business standpoint, someone looking at it should understand the actual business of the whole
> application — the complete end-to-end business flow — not the pages or objects. The terms 'bundle', 'object', etc. should
> not appear. Give me a high-level business flow / constellation that explains the complete business of the application. An
> agent should build this."*

Net: Phase 16 made Genesis **own** the knowledge; Phase 17 makes Genesis **explain** it — in the language of the business, for
a human audience, produced by an agent that interprets the technical KB into a business narrative.

**Why an agent (and not a mechanical render).** The KB is *technical structure*; "business meaning" is not a field in it.
Turning record types into *business entities*, entry-point processes/actions into *business activities*, and the dependency
graph into an *end-to-end journey* — expressed in a domain's own language — is an act of **interpretation**. That is precisely
what a narrow, well-grounded agent step is for, and Genesis already has the machinery to do it safely (deterministic workflow,
per-node MCP injection, the reliability trio, real credit metering, the `design-doc` precedent of synthesizing narrative from
Appian data). A purely heuristic grouping (cluster by name/dependency) can seed the evidence but cannot produce a coherent,
readable business story — so the *synthesis* is agent-driven and the *grounding* is deterministic.

## 2. Background — what we have to build on

**The Phase-16 KB (verified, code-free).** `genesis.db` holds a temporal (SCD-2) model of a tracked app: `kb_objects`
(type, name, description, `is_entry_point`/`entry_point_kind`, `is_orphan`, `metadata_json`), `kb_dependencies` (typed
edges), `kb_bundles` (entry-point bundles with a verbatim process **`flow_json`** = BPMN-style nodes + `next` + gateway
conditions + writes + subprocess/interface refs), `kb_bundle_members`, `kb_syncs`, `kb_releases`. Read via `KbStore`
(`get_app_overview`, `search_objects`, `get_object`, `get_bundle` [returns flow], `get_dependencies`,
`get_entry_points_for_object`, `get_hub_objects`, `get_dependency_path`, `get_transitive_dependencies`, …) and served
read-only by the **`genesis-kb` MCP** (Phase 16-05). **No source code is stored** (ADR-037).

**The business signal already latent in that technical data** (this is the raw material the agent interprets — the mapping is
made concrete in `business-model-contract.md` §3):

| KB signal | → Business concept |
|---|---|
| **Record types** (+ names/descriptions, lifecycle/state fields) | **Business entities** — the nouns the business deals with (Document, Invoice, Case, Customer). |
| **Entry-point process models + record actions** (+ their `flow_json` stage names, gateway labels, write targets) | **Business activities / stages** — the verbs ("Submit", "Review", "Approve", "Archive") and the journey's ordering + branches. |
| **Sites / dashboards / control panels** | **Business surfaces** — where users do the work (used as context; never shown as "pages"). |
| **AI skills / integrations / connected systems** | **Capabilities** — notably automation ("AI classification") and external touchpoints. |
| **Groups** | **Actors / roles** — who performs an activity. |
| **Dependency graph + bundles + hub objects** | **Hand-offs & cohesion** — how activities touch entities and how capabilities connect. |

**Genesis machinery reused.** Deterministic LangGraph workflow with narrow agent nodes (ADR-001); the reliability trio
(validator + retry + escalation, ADR-011); per-node MCP injection of the read-only `genesis-kb` (ADR-002/005/031); the
run blackboard for bulk intermediates (ADR-010/018); real per-turn credit metering (ADR-032); `genesis.db` migrations for
persistence (ADR-030, code-free per ADR-037); the web's existing **`@xyflow/react` + `@dagrejs/dagre`** stack (already used
by the run-detail graph) for rendering (ADR-026/027).

## 3. What the Business Map depicts (the two views)

The single source of truth is the **`BusinessModel`** artifact (contract: `business-model-contract.md`). The web renders it as
two **coordinated** canvases sharing one selection:

### (A) Business value stream — "the complete business flow"
A left-to-right flow of **business stages**. Each stage is a business step (not a technical node), carrying: a business
**name**, a short **description**, the **actor** who performs it, the **entity** it acts on, its **capability**, and its
**kind** (`start` | `activity` | `decision` | `end`). **Decisions** branch with business-worded labels ("Approved" /
"Rejected" / "Needs info"). An app may have more than one value stream (e.g. a primary journey + a secondary admin journey);
each is a small, readable DAG (single logical start, reachable end). A stage backed by a self-contained sub-journey can be
**expanded**. This is the view that answers *"walk me through what this application does."*

### (B) Business capability constellation — "what is this app about"
A small set of **capabilities** (functional areas — typically 4–10) arranged around the business **domain**, with the core
**entities** and **capability→capability hand-off** edges. It is the zoom-out overview: one glance conveys the app's purpose
and shape. Clicking a capability filters/highlights the value stream to the stages that belong to it (and back) — **focus +
context linking/brushing**, the antidote to a "clustery" diagram.

**Business language is mandatory.** Node labels, descriptions, the summary, and the domain are all in business terms. The
technical origin (which KB objects each element came from) is retained as **hidden evidence** for traceability and an optional
"see the underlying objects" affordance (off by default) — it is never part of the primary display, and the banned-token guard
(see §5) keeps technical vocabulary out.

## 4. Architecture — how it is produced (`generate-business-map` workflow)

A **deterministic** LangGraph workflow in `genesis-workflows`; **program** nodes own control flow, **agent** nodes only
interpret, and **every agent node is wrapped by the reliability trio** (validator + retry + escalation, ADR-011). It reads the
**local KB only** (no environment call), so inputs are deterministic and generation is fast + offline.

**Topology** (program nodes plain, agent nodes marked 🤖, validators `v_*`):

```
resolve_inputs → extract_evidence → v_evidence
  → 🤖 synthesize_capabilities → v_capabilities
  → 🤖 synthesize_value_streams → v_value_streams
  → compose_model → v_model
  → review (HITL approval gate)
  → persist_map → present
```

1. **`resolve_inputs`** (program) — resolve `app_uuid`; require a **completed baseline sync**; select `source_sync_id`
   (latest, or a named release). Fail fast with a clear message if the app is not synced.
2. **`extract_evidence`** (program) — assemble a **Business Evidence Pack** from `KbStore` (17-02): entities (record types +
   descriptions), activities (entry-point processes + record actions with their `flow_json` **stage names**, gateway labels,
   and write targets), surfaces (sites/dashboards), capability-signals (AI skills, integrations, connected systems), actors
   (groups), hub objects, bundles-by-type, and counts. **Compact + capped** to fit the context window (summarized — never the
   full multi-thousand-object dump). Written to the blackboard as `evidence.json`.
3. **`v_evidence`** (validator) — schema + non-empty; at least one entity and one activity (else the app can't yield a
   business story → fail with guidance).
4. **`synthesize_capabilities`** 🤖 (`genesis-kb` read tools injected for drill-downs) — from the evidence pack, produce the
   business **summary**, **domain**, **entities**, **capabilities** (+ capability relations), and **actors** — **(B)** — each
   element citing its **evidence** UUIDs. Prompt enforces business language.
5. **`v_capabilities`** (validator) — JSON-schema; **evidence integrity** (every cited UUID exists in the KB, checked against
   `KbStore`); **coverage ≥ threshold**; **business-language guard** (banned technical tokens). Retry on fail; escalate on
   exhaustion.
6. **`synthesize_value_streams`** 🤖 — from entities + capabilities + the activity flows, produce the end-to-end **value
   stream(s)** — **(A)** — ordered stages with branches, each tied to a capability/entity/actor + evidence + `kind`.
7. **`v_value_streams`** (validator) — schema; **DAG well-formedness** (single logical start, reachable `end`, no dangling
   `next`, decisions carry branch conditions); evidence integrity; language guard.
8. **`compose_model`** (program) — merge into the `BusinessModel v1`; compute **coverage** metrics + cross-reference integrity
   (every stage's capability/entity id exists in the model). Written as `business_model.json`.
9. **`v_model`** (validator) — full-contract validation + coverage gate + cross-ref integrity.
10. **`review`** (HITL **approval** gate, ADR-021; escalations also land here) — the human accepts the map or requests changes
    (quality/trust). Configurable to auto-approve for unattended regeneration.
11. **`persist_map`** (program, **async node**) — upsert the current `BusinessModel` row into `kb_business_maps` with
    `source_sync_id`, `generated_at`, `run_id`, `credits`, `coverage`, `status='ready'`. The blocking `KbStore` write runs via
    **`asyncio.to_thread`** (Phase-16-03 lesson: never block the event loop / checkpointer).
12. **`present`** (program) — summary + pointer + coverage + credits.

**MCP:** only the read-only **`genesis-kb`** is injected (per-node read-tool allowlist; effective trust = `node.tools ∩
server.allowlist`). No environment MCP, no write tools. **Credits** are real (ADR-032) — generation cost is surfaced.

## 5. Trust: evidence-grounding, coverage & the business-language guard

The single biggest risk of an agent-authored diagram is a confident, wrong story. Three program guards (all in `v_*` nodes,
detailed in `business-model-contract.md` §4 and hardened in 17-06) make the map trustworthy:

- **Evidence integrity (anti-hallucination).** Every capability/entity/stage/actor declares the KB **object UUIDs** it was
  derived from. A validator resolves each UUID against `KbStore`; any element referencing a non-existent object fails the node
  → retry with the failure detail → escalate to `review`. The agent cannot invent objects.
- **Coverage gate.** The model must explain at least a configurable fraction of the app's *significant* objects (entry points,
  record types, key processes). Low coverage ⇒ the story is too thin ⇒ fail/escalate. Coverage is surfaced in the UI ("{n}% of
  the application is represented").
- **Business-language guard.** A banned-token check rejects technical vocabulary in business-facing fields (`object`,
  `bundle`, `interface`, `expression rule`, `record type`, `process model`, raw UUIDs in labels, etc.), keeping the output in
  the business register.
- **Human review gate.** Final acceptance is a person (ADR-021); escalations from any validator surface here with the specific
  failure. This is the trust backstop, not a substitute for the automated guards.

## 6. Persistence — migration `m0008` (`kb_business_maps`)

Schema owned by `genesis/db/` (add a migration; never hand-write DDL). Code-free business metadata (ADR-037), DB-agnostic
signatures (ADR-030).

```
kb_business_maps(
  id             INTEGER PK,
  app_uuid       TEXT NOT NULL REFERENCES kb_applications(app_uuid) ON DELETE CASCADE,
  schema_version INTEGER NOT NULL,          -- BusinessModel contract version (starts at 1)
  source_sync_id INTEGER,                   -- the sync this map was generated from (point-in-time grounding)
  model_json     TEXT NOT NULL,             -- the full BusinessModel v1 (business metadata only, NO code)
  summary        TEXT,                      -- denormalized for quick list/label display
  domain         TEXT,
  coverage_json  TEXT,                      -- coverage metrics
  status         TEXT NOT NULL,             -- generating | ready | failed | stale
  run_id         TEXT,                      -- the generate-business-map run
  credits        REAL,                      -- metered generation cost (ADR-032)
  generated_at   TEXT,
  release_label  TEXT,                      -- NULL = current map; named = release snapshot (future)
  UNIQUE(app_uuid, release_label)           -- one current map per app; release snapshots land later
)
```

`KbStore` gains `upsert_business_map` / `get_business_map` / `business_map_status`, and a **stale hook**: when a newer sync
completes, the current map is marked `stale` so the UI can prompt a regenerate. One current map per app (overwrite on
regenerate); release snapshots are schema-ready for a later phase (mirrors `kb_bundles.release_label`).

## 7. API + Web

**API** (`genesis/api/applications.py`, all under `/api`, ADR-028):
- `GET  /api/applications/{uuid}/business-map` → `{status, model?, source_sync_id?, generated_at?, credits?, coverage?, stale?}`
  (`status:"absent"` when never generated).
- `POST /api/applications/{uuid}/business-map/generate` → launches `generate-business-map` via `RunManager` (KB-only; no env
  needed) → `{run_id}`.
- `GET  /api/applications/{uuid}/business-map/status` → merged run status + row status (mirrors `sync-status`).

**Web** (`web/src/features/applications`): a new **"Business Map"** view, made the **primary/first** thing on the application
detail page (the existing technical Overview/Objects/Bundles/Syncs/Releases tabs remain, grouped under a secondary
"Technical" area — their eventual relabel/retirement is an **open decision**, not part of 17's core). Empty state → a
"Generate business map" button (→ POST generate → live status via the run). When ready it shows *"based on sync #N · generated
{when} · {credits} credits · {coverage}% covered"*, a **Regenerate** action, and a **stale** banner when a newer sync exists.

Rendering reuses **`@xyflow/react` + `@dagrejs/dagre`** with **new business-styled node/edge components** (NOT the technical
`NodeCard`), design tokens per ADR-027:
- **(A) Value stream** canvas — horizontal staged flow; stage cards (name, actor, entity chip); decision diamonds with branch
  labels; start/end markers; expandable sub-journeys.
- **(B) Capability constellation** canvas — capabilities clustered around the domain center; entity nodes; capability hand-off
  edges.
- A segmented control toggles/splits A ↔ B; a shared selection **links** them (click a capability → its stages highlight;
  click a stage → its capability highlights). Each node has an optional plain-language "what & why" popover (from evidence);
  the "see underlying objects" link to the technical view is present but off by default (keeps it business-clean).

## 9. Non-goals (explicit)

- **Not a technical graph.** No objects, bundles, pages, interfaces, record types, or object properties in the output; those
  terms are banned from the business vocabulary. A technical/architecture visualization is a **separate, later** effort.
- **No environment round-trip.** Generation reads the **local KB only** (fast, offline, deterministic). No live env calls, no
  writing to Appian.
- **No source code.** The map is business metadata (ADR-037); "view code" is not part of it.
- **Not real-time.** The map is point-in-time (tied to a sync) and regenerated on demand; a newer sync marks it stale.
- **Not multi-user.** Local single-user, like the rest of Genesis (ADR-026).
