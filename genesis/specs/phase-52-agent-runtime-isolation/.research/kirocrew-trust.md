# KiroCrew (fb81cec80f, 2026-11-17) — trust and isolation design, compared with Genesis Phase 52

Paths are under /Users/ramaswamy.u/repo/KiroCrew. **V** = verified in code or doc at the cited line. **I** = inferred.
KiroCrew is a different shape from Genesis: the gateway AND the agents run in one container/host process tree, and the agent is confined by an in-process OS sandbox (bwrap/seatbelt) plus a Python tool gate, not by a separate sandbox container. Several of our decisions have no direct KiroCrew counterpart.

## 1. Kiro auth (KAS host auth)

- **Spawn recipe (V).** `kiro-cli-chat acp --agent-engine v3 --auth-method client`. Crew enters through `kiro-cli-chat` (the `chat_sibling`) because the `kiro-cli` launcher below 3.0.0 checks its own sign-in before exec, so a signed-out host dies with "You are not logged in" before the engine asks for a token: `acp/harness/kas.py:936-975`, `docs/system-specs/modules/kas-auth.md:14-24`. From kiro-cli 3.0.0 `kiro-cli` is the chat binary itself and no sibling is used (`kas-auth.md:19-21`, `kiro_cli.py:312`). Never swapped when the operator set `KIROCREW_KIRO_BIN` (`kas.py:~960`).
- **Flag rule (V).** `--auth-method client` is passed unless the version is known to be below 2.35.2 (`kiro_cli.py:142`, `:301-309`). Unknown version gets the flag, because an old release rejects the value at argument parse, which fails closed. From 2.35.2 an omitted flag means `cli` (kiro-cli answers from its own store), so omission is unsafe (`kas-auth.md:8-13`).
- **Env (V).** For a Crew-owned relay `KIROCREW`'s `apply_spawn_env` strips `KIRO_API_KEY`, since the engine prefers an env key over the callback (`kas-auth.md:30-34`; `kas_host_auth.py:73-77` also sets `allow_env_api_key=False`).
- **Callback response (V).** `{accessToken, expiresAt (ISO-8601, must be at least now+3min), profileArn?, authMethod?, provider?}`; no refresh token (`kas-auth.md:107-121`, `kas_host_auth.py:58-66`). `profileArn` is effectively mandatory: without it the Kiro runtime answers 400 "profileArn is required" (`kas-auth.md` §Identity classification, ~line 140). Builder ID gets a fixed ARN constant. `provider` drives governance (BuilderId/Google/Github/Enterprise/ExternalIdp/Internal).
- **Refresh (V).** Crew runs its OWN OIDC lifecycle and its own sign-in (device-code, loopback PKCE, SSO-OIDC, external IdP). It does NOT read kiro-cli's store when Crew-owned. Under a cross-process single-flight lock, `ensure_fresh` guarantees expiry ≥ now+3min on every query (`kas-auth.md:312-330`); a gateway tick refreshes ahead of time even when idle (`kas-auth.md:331-348`). A refusal (400/401/403) writes a marker and is shown to the user, never silently handed back to kiro-cli's login (`kas-auth.md:~584-600`). Failures are returned to the engine as token-free categories ("not signed in", "refresh failed"): `kas_host_auth.py:78-90`. The engine does not wedge on refusal: it re-asks about twice a second and `session/prompt` fails -32000 (`kas-auth.md:576-583`).
- **Token store (V).** Dedicated AES-256-GCM vault at `<data_home>/kas/.vault`, hidden from the agent and from the OS sandbox (`kas-auth.md:369-400`). kiro-cli's own store is plaintext SQLite `auth_kv` 0600 (`kas-auth.md:371-373`).
- **Tested range (V).** `KIRO_CLI_TESTED_RANGE = ((2,27,0),(4,0,0))`, i.e. 2.27.0 up to but not including 4.0.0; a warning only, session still runs (`acp/client_turn_control.py:190-199`, `:269-290`; commit 1dee6bb8ed, 2026-11-15). Auth-client live measurements: 2.21.0 and 2.35.1 (flag omitted), 2.35.2 parse, 2.37.1 and 3.0.0 signed-out callback is the first frame (`kas-auth.md:565-575`). **`--auth-method client` with kiro-cli signed in is unmeasured** (`kas-auth.md:575`). Docker pins one kiro-cli in `packaging/kiro-cli-version` with a sha256 file (`docker/Dockerfile:30-36`).
- **Credits in client mode (V for source, I for the combination).** Per-turn credits come from the `turn_completion` frame, `credit` units only (`acp/kas_wire.py:75`, `:155-158`; older `meteringUsage` path `acp/client_usage.py:162-177`). That frame is engine-to-ACP-client and independent of who answered auth, so metered credits should still flow (I). Account-level credit reading uses `GetUsageLimits` with the vault bearer; for an API-key identity that call is skipped and `/usage` is scraped (`kas-auth.md:449-454`, `:600-619`).

## 2. Secrets

- **Vault (V).** Per-entry AES-256-GCM, key file beside it, in `<data_home>/.vault`. Protection is "enforced by Kiro Crew, not by the operating system: another program running as you can still open the files" (`src/kiro_crew/docs/secrets-vault.md:3-19`). Enabled for everyone by 8e5b638283 (2026-11-17). Read audit (5ceb58b950) is default-off setting `dashboard.audit_secret_reads`: logs secret name, module and function, never the value, with 10-minute dedupe (`secrets-vault.md:21-34`).
- **MCP secrets (V).** `secret://NAME[#FIELD]` in an MCP server's env is resolved in memory at spawn by gatewayd, never persisted (`mcp_gateway/secret_uri.py:1-10`).
- **Mediated requests (V).** The agent names a secret and a URL; trusted code sends the request and returns a fixed withheld result. Owner pre-authorizes secret→exact https origin→placement (bearer or one named header) with `kirocrew secrets authorize`, HMAC-signed with an owner key in a sandbox-hidden dir; an unsigned or hand-edited policy is refused (`secrets_mediation/policy.py:1-43`). Dispatch order: authorization → origin equality → SSRF vet + address pinning → resolve secret → send, redirects manual and only same-origin, response withheld (status fixed at 0 to block a covert channel), writes only (POST/PUT/PATCH/DELETE), body ≤256 KB, ≤60 s (`secrets_mediation/dispatch.py:1-32`, `:61-77`).
- **Browser login fill (V).** Crew types username/password into the page; the agent only learns success (`secrets-vault.md:59-66`).
- **Env scrub (V).** `scrub_agent_subprocess_env` drops credential prefixes (AWS, SSH_AUTH_SOCK, GNUPGHOME, GIT_ASKPASS, channel tokens) from every agent child; `agent.env` overlay is applied before the scrub and a name the scrub removes is dropped with a warning (`sandbox_spawn.py:450-475`, `:505-530`; `acp/agent_env.py:1-60`). On the default `standard` tier AWS/SSH/GPG variables are deliberately kept so git-over-SSH and the AWS CLI work (`sandbox_spawn.py:~545-552`). The container entrypoint moves channel and `KIRO_API_KEY` env into a 0600 `.env` and scrubs them from the gateway's environment (`docker/compose.yaml:33-36`, `docker/entrypoint.sh:64-116`).
- **MCP credentials on the wire (V).** The KAS projection withholds every MCP `env` and `headers` value except literal booleans and `${NAME}` references the edition whitelists (default list is empty) and `KIROCREW_HOME` for managed servers (`acp/kas_env_withhold.py:15-61`, `kas_agents_mcp_servers.py:50-56`).
- **Redaction (V).** 028c39db49 made redaction one owner switch, **off by default**, hiding nothing from the owner's own sessions but still redacting for non-owners, apps, links and the security log (`docs/decisions/2026-11-15-credential-redaction-off-by-default.md`). Crew moved away from redaction as a primary control; the controls that matter are path denial and not handing the agent the secret.

## 3. MCP

- **Gateway (V).** Not HTTP. `mcp_gateway/` is a local daemon (gatewayd) that pools stdio MCP backends across sessions. kiro-cli execs a tiny **stub** instead of the real MCP binary; the stub connects to gatewayd over a unix socket (peer-uid check via SO_PEERCRED / LOCAL_PEERCRED / named-pipe SID, fail closed: `mcp_gateway/socketsec.py:1-30`) and registers with a per-session **stub token** in its env (`session_servers.py:1-25`, `stub.py:1-22`). Stub entries carry `env: {}` apart from the token, so no credential is sent in `session/new`. gatewayd resolves the real command and env itself from `KIROCREW_MCP_TARGET_<SERVER>` in its own environment (`session_servers.py:~35-48`).
- **Session injection (V).** kiro-cli `session/new` accepts an `mcpServers` array and a session-injected server wins over a same-named agent-spec entry (`session_servers.py:1-12`); `acp/session_mcp.py:203-205` builds remote entries as `http` (streamable) or `sse`; `client_mcp_array.py` composes the array.
- **HTTP MCP on KAS (V).** KAS accepts remote entries as `url/headers/env/timeout`; `type` is stripped by its schema, a plain `http://` URL to a non-loopback host is refused by KAS (`acp/kas_tool_limits.py:15-39`, `kas_agents_mcp_servers.py:66-70`). Static `Authorization` headers are withheld from the wire (`kas_agents_mcp_servers.py:52-56`, `kas_env_withhold.py:20-23`). I found no use of an HTTP MCP gateway with per-turn tokens; their remote-server path is for user-added third-party servers.
- **Tool allowlisting (V, partly).** Enforced by the engine, not by an MCP server: the projected agent has `tools` plus `excludedTools` (disabled tools become engine `excludedTools`, `kas_tool_limits.py:27-34`, `:55-65`) and a `permissions` rules list keyed by capability+glob such as `{"capability":"mcp","match":["srv/*"],"effect":"allow"}`; an unmatched call resolves to `ask` (`acp/kas_permissions.py:1-46`). `autoApprove` verbs become `@server/tool` grants and pass the governance ceiling (`acp/kas_auto_approve.py:1-18`). Server-side enforcement in gatewayd is not an allowlist; `mcp_gateway/rewriter_spec.py:486` only reads a `tools` allowlist for the stub.
- **Mount check (V).** `acp/mcp_mount_check.py:1-30` detects a stub that never registered (goose drops unstartable servers silently) by asking gatewayd which stub tokens arrived.

## 4. Permissions

- **No `--trust-tools` (V by absence).** grep finds no `trust-tools`, `trust_tools` or `--trust-all` in `src/kiro_crew` apart from the MCP stub's own `--trust-all` argparse flag (`mcp_gateway/stub.py:149`). Trust on KAS is expressed as the inline `permissions` rules and `allowedTools`-derived allows in `customAgents`, not as flags.
- **Built-ins are deliberately NOT auto-approved in the engine (V).** `WITHHELD_FROM_AUTO_APPROVE` = fs_read/read/grep/glob/code, fs_write/fs_append/str_replace/write, execute_bash/execute_pwsh and the two process controls (`kas_permissions.py:154-174`). A spec that asks for them gets no allow rule, so every call raises `session/request_permission`; Crew's gate then answers on the spec's behalf in the `spec-builtin-grant` tier, placed after the deny floor, sensitive-path and governance checks (`hook_runtime/gate_tiers.py:1587-1610`; `kas_permissions.py:142-153`). `code` is never answered as a whole (`:631-633`). Reason given: an engine allow rule means no permission request, so the deny floor never runs (`kas_permissions.py:25-27`).
- **Gate order (V).** `HookManager.judge` walks `GATE_TIERS` in order; deny tiers before any auto-approve or trust fast-path (`gate_tiers.py:1-9`, `docs/architecture/security-deep-dive.md:82-86`). Governance ceiling can withhold built-in grants (`kas_permissions.py:598-616`).
- **Write allowlist (V).** `fallbackAction: "deny"` + `fs_write.allowedPaths` become a session write allowlist the gate matches (`kas_write_allowlist.py:1-50`).

## 5. Egress

- **Still a documented gap (V).** "No network egress control by default": the sandbox hides credential files but not outbound network; a network namespace or host firewall allowlist "would close it" (`docs/architecture/security-deep-dive.md:727-733`).
- **`network.egress` governance scope (V).** Applies only to the dedicated `fetch` tool, by host; shell egress (curl, git, python) is not covered and the docs call it defense-in-depth, not a bound (`docs/system-specs/modules/governance.md:3060-3077`). The remote-session git proxy checks `network.egress` for github/gitlab/bitbucket/dev.azure before each request (`governance.md:3078-3082`).
- **Approved sites (V).** a72d85d645: an app's `permissions.browserSites` (exact https origin + path pattern, owner-approved) auto-approves the `browser` tool and the browser-op route refuses pages off the list (`apps/browser_sites.py:1-30`). Browser capture has an SSRF guard but a DNS-rebinding window is "ACCEPTED, bounded" (`security-deep-dive.md:836-846`).
- **Proxy design (V by absence).** None. The only proxy code is `HTTPS_PROXY` support for sign-in traffic (`kas-auth.md:351-367`).

## 6. Local API auth

- **Tokens (V).** HMAC-SHA256 signed time-limited URL tokens minted by the owner (`kirocrew token`, `!dashboard`), exchanged for an access cookie plus refresh cookie (`mc_refresh_{port}`, path `/api/auth`), refresh-token rotation with chain-head-only grace (`dashboard-token-auth.md:1-9`, `:27-35`). Persistent signing key `token_signing.key`, revocation generation, `kirocrew logout` (`:7`). Token is pinned to a peer key (client IP or Tailscale identity) (`:5`).
- **Loopback is not trusted (V).** Ordinary loopback requests still require a token (`dashboard-token-auth.md:388`, test `test_loopback_requires_token`). Internal routes use loopback + `X-Internal-Secret` (the `.local_secret` file), and POSIX adds a same-uid unix socket where the peer identity is kernel-attested (`:868-885`). `/api/token/local` is a bypass route that self-authenticates with `X-Local-Secret` and a verified host process (`:392`).
- **Origin/Host (V).** `dashboard/origin.py:1-18` is the shared CSRF/WebSocket origin check; Host barrier + POST CSRF apply to every request except three probe paths (`docker/Dockerfile:25-29`, `dashboard-token-auth.md:22-24`, `:123`). Allowed origins derive from the single `dashboard.url`.
- **CLI and tests (V for CLI, I for tests).** CLI mints via `kirocrew token --ttl 2h` (`docker/compose.yaml:5`) or the secret file; tests that need tokens use the helpers in `test_loopback_requires_token` and related files (not read).

## 7. Data, state, container

- **State (V).** One home: `~/.kiro/crew` plus kiro-cli credentials, agents, skills, all under `/home/kirocrew` in the image, one named volume `kirocrew-home` (`docker/compose.yaml:24-28,63-64`, `docker/Dockerfile:19-22`, `docs/guides/docker.md:136-142`). kiro-cli binaries live at `/usr/local/bin`, outside the volume, so a mounted home cannot shadow them (`Dockerfile:30-36`); the KAS bundle likewise at `/usr/local/share/kirocrew/kas`, root-owned (`docker.md:504`).
- **Backup/restore (V partial).** No volume backup/restore procedure found in `docs/guides/docker.md`. There is a "portability" export/import feature in the dashboard API (`dashboard-token-auth.md:~45`, `cli.md`), not read in detail.
- **Image updates (V).** fdf7cbc2ec: the update check reads the release feed, confirms the image tag on GHCR with an anonymous token + manifest HEAD (5 s, no redirects), and About shows "Version X is available as a container image". Nothing applies it; the user pulls and recreates with the same volume (`dashboard/handlers/_update_image.py`, commit message; `docker.md:136-150`).
- **Sandbox inside the container (V).** Entry probes for a working user-namespace sandbox; if none, agent exec is DISABLED unless `KIROCREW_ALLOW_UNSANDBOXED=1` (container as only boundary, "do not mount host paths you would not hand to the agent"); a custom seccomp profile re-enables the inner sandbox (`compose.yaml:49-57`, `docker.md:225-236`, `docker/entrypoint.sh:18-31`, `docker/seccomp/`). Loopback-only port publish by default (`compose.yaml:15-23`).

## Implications for Genesis D7–D17

I only know the decision text you gave me, not the D-numbers. Mapped by topic.

- **MCP gateway outside the sandbox, per-turn token (supports, and extends).** KiroCrew's stub token + gatewayd with credentials held only on the gatewayd side and `env: {}` in `session/new` is the same trust split. Differences: theirs is a unix-socket stdio pool with a peer-uid check; yours is HTTP with a per-turn token. They do not enforce tool allowlists in the gateway (the engine does, via `tools`/`excludedTools`/`permissions`), so server-side allowlisting in the gateway is **additional** assurance. Keep the engine-side projected allowlist as well (defence in depth). Also adopt their **mount check** idea: detect that a session's MCP servers actually connected and surface a failure instead of silent drop (`mcp_mount_check.py`).
- **Withhold credentials from `session/new` (supports; add).** Their projection strips all `env` and `headers` from MCP entries (`kas_env_withhold.py`). Do the same for any server entry that still reaches the sandbox, and fail closed on unknown fields.
- **Token broker, `--auth-method client` (supports).** The recipe is identical (`kiro-cli-chat acp --agent-engine v3 --auth-method client`, response shape, ≥3 min expiry, no refresh token). Add: (a) the version floor 2.35.2 and "unknown version passes the flag"; (b) strip `KIRO_API_KEY` from the sandbox env because the engine prefers it over the callback; (c) include `profileArn` or requests fail with 400; (d) token-free error categories and an idle refresh tick; (e) their **range 2.27.0–<4.0.0** as a warning range. Contradiction to note: KiroCrew runs its own OIDC login and refresh; your broker must still get the refresh token from somewhere (kiro-cli's store on the host, or your own sign-in). They never read kiro-cli's store in client mode. `--auth-method client` with a signed-in kiro-cli is unmeasured by them; measure it before relying on it.
- **Built-ins auto-approved in the sandbox (contradicts their approach, fits yours).** KiroCrew keeps shell/fs at `ask` and answers in its own gate after deny-floor checks, because its agent shares the host. With a real sandbox boundary, engine auto-approve is defensible; just record that you lose any Genesis-side deny floor and path checks on those calls. If you keep a few host-side checks (e.g. paths under the mounted blackboard), use their pattern: no allow rule, answer `session/request_permission` yourself after the checks. V3 does not take `--trust-tools`; they express trust only through the projected agent's `permissions`/`allowedTools` (matches L-113).
- **Chat read-only (supports).** Capability-keyed `permissions` with `fallbackAction: deny` and a write allowlist is their equivalent (`kas_write_allowlist.py`).
- **Egress default-deny proxy (they have none; yours is new ground).** Their own docs call the lack of default egress control a known gap and name a network namespace or allowlist as the fix. Nothing to copy. Take their lessons: host-only rules do not cover shell egress, so the sandbox must have no direct route and only the proxy; pin resolved addresses and re-vet on redirect (their mediated dispatch does this, `dispatch.py:1-32`); DNS rebinding remains if the proxy resolves after the check.
- **Secrets never inside the sandbox (supports, with a stronger variant to add).** Their mediation (secret→exact origin→placement, owner-signed policy, withheld response with fixed status) lets an agent use an API secret without seeing it. You could offer this through the gateway for workflow-declared API calls. Their vault protection is software-only and admitted as such (`secrets-vault.md:15-19`); a separate trusted container is stronger.
- **Local API token + Origin/Host (supports).** They require a token even on loopback, a persistent signing key, rotating refresh cookies, Host + Origin checks, and a unix socket with kernel-attested peer identity for local CLI. Your per-launch token is simpler; consider also persisting nothing across launches (their persisted key survives restarts, yours need not) and an `X-Local-Secret`-style bootstrap for the CLI.
- **Volumes, backup, image updates (partly supports).** One named volume for everything, tool binaries outside the volume, anonymous GHCR manifest check for update notice, recreate-with-same-volume upgrade. They offer no volume backup/restore recipe, so your backup/restore decision is additional work; do not expect a reference.
- **Redaction (neutral).** They made redaction off by default for the owner; Genesis already treats secrets as never-in-sandbox, so keep redaction only for logs and non-owner sinks.
