# Solutions Intelligence Knowledge Base — T-Retriever Navigation Pattern

## What Is This

The Solutions Intelligence Knowledge Base (KB) is a pre-computed intelligence layer that lives entirely inside Appian. A Java plugin parses every object in an application and generates structured JSON documents — app tree, clusters, dependency graph, object content with resolved UUIDs, data model, patterns, architecture, security audit, and dead code analysis.

The KB eliminates the need for repeated live API calls to understand an application. Instead of making 10-20 calls to search, fetch, and trace dependencies, the KB provides the same information in 1-3 calls through a tiered retrieval pattern.

## When to Use KB vs Live API

| Use KB (solutions-intelligence_* tools) | Use Live API (existing MCP tools) |
|--------------------------|-----------------------------------|
| Understanding application structure | Creating or deploying objects |
| Researching how a feature works | Evaluating SAIL expressions |
| Finding objects by name, type, tag, or pattern | Getting current constant values |
| Tracing dependencies and impact | Checking real-time data (query_sql) |
| Reading SAIL code with resolved UUIDs | Fetching object diffs (get_object_diff) |
| Exploring data model and relationships | Package operations (inspect, deploy) |
| Identifying dead code or shared utilities | Searching recently created objects not yet in KB |
| Understanding architecture and layers | Writing to the environment |
| Design research — "how is X implemented?" | |
| Code review pre-analysis — understanding context | |

**Rule of thumb:** KB for reading/understanding, live API for writing/current-state.

**Important:** The KB is a snapshot generated by the plugin. Objects created after the last KB generation won't appear. For recently created objects, fall back to live API tools (`lcp-api.searchObjects`, `lcp-api.listApplications`, `lcp-api.searchObjects`).

## Resolving app_name

Every KB tool requires `app_name` — the Appian folder ID where the KB documents live.

**Lookup process:**
1. Call `solutions-intelligence.list_applications` to get the list of registered applications
2. Find the application by matching `appPrefix`, `appName`, or `jiraProjects`
3. Use the `app_name` field from the matched application's `appConfig`

**Example response structure:**
```json
{
  "appConfig": {
    "appPrefix": "AS_VM",
    "app_name": 1510447
  },
  "staleCount": 0
}
```

If `app_name` is null or empty for an application, the KB has not been generated for it yet. Fall back to live API tools.

## The T-Retriever Pattern

Navigate the KB in tiers — start broad, drill down only as needed. Each tier adds detail but costs more context.

```
L0: App Tree (shape)     → 1 call, ~2KB
 └─ L1: Cluster / Search → 1 call, ~5-20KB
     └─ L2: Analysis      → 1 call, ~2-10KB
         └─ L3: Content    → 1 call, ~5-50KB per object
```

### L0 — Application Overview

**Tool:** `solutions-intelligence.get_app_overview`
**Cost:** 1 call
**Returns:** App metadata, entry points grouped by type (site pages, record actions, web APIs, scheduled processes), type counts, cluster summary with sizes.

**Use when:**
- Starting work on an unfamiliar application
- Need to understand the application shape before diving in
- Looking for the right entry point to investigate
- Need type counts or cluster list

**What you learn:** How big is the app, what are the main features, where are the entry points.

### L1 — Feature Drill-Down

**Tools:** `solutions-intelligence.get_bundle`, `solutions-intelligence.search_objects`, `solutions-intelligence_get_objects_by_type`

| Tool | Use When |
|------|----------|
| `solutions-intelligence.get_bundle` | You know which feature/entry point to explore. Use exact cluster name from app-tree. |
| `solutions-intelligence.search_objects` | You're looking for something specific — searches name, description, type, and tags. |
| `solutions-intelligence_get_objects_by_type` | You want all objects of a type (e.g., all integrations, all record types). |

**Cost:** 1 call each
**Returns:** Object lists with metadata — name, type, description, tags, complexity, cluster membership.

**What you learn:** Which objects are involved in a feature, what they do, how complex they are.

### L2 — Relationship & Analysis

**Tools:** `solutions-intelligence.get_dependencies`, `solutions-intelligence.get_transitive_dependencies`, `solutions-intelligence_get_entry_points_for_object`, `solutions-intelligence.get_app_schema`, `solutions-intelligence.get_hub_objects`

| Tool | Use When |
|------|----------|
| `solutions-intelligence.get_dependencies` | "What does X call?" / "What calls X?" — focused 1-hop view |
| `solutions-intelligence.get_transitive_dependencies` | "What breaks if I change X?" — full blast radius with transitive callers |
| `solutions-intelligence.get_dependencies` | "What depends on these 5 groups?" — direct dependents for multiple objects in one call. Use instead of repeated `solutions-intelligence.get_transitive_dependencies` when querying 3+ objects |
| `solutions-intelligence.get_dependencies` | "What do these interfaces call?" — direct precedents for multiple objects in one call. Use instead of repeated `solutions-intelligence.get_dependencies` when querying 3+ objects |
| `solutions-intelligence_get_entry_points_for_object` | "Which features use X?" — inverse of cluster lookup |
| `solutions-intelligence.get_app_schema` | "How are records related?" — fields, relationships, data stores |
| `solutions-intelligence.get_hub_objects` | "What's shared across features?" — cross-cluster utilities |

**Cost:** 1 call each
**Returns:** Dependency edges, impact trees, data model structure, cross-cluster mappings.

**What you learn:** How objects connect, what the blast radius is, how data flows.

### L3 — Full Object Detail

**Tools:** `solutions-intelligence.get_object_code`, `solutions-intelligence.get_object_detail`, `solutions-intelligence_get_object_xml`

| Tool | Use When |
|------|----------|
| `solutions-intelligence.get_object_code` | Need the SAIL code / PM nodes / record config for one object |
| `solutions-intelligence.get_object_detail` | Need everything about one object in a single call — content + deps + metadata + impact + clusters |
| `solutions-intelligence_get_object_xml` | Need the raw deployable XML for object creation/modification |

**Cost:** 1 call each, but L3 content can be large (5-50KB per object)
**Returns:** Full SAIL code with resolved UUIDs, process model node details, record type fields and relationships, raw XML.

**What you learn:** Exactly how the object is implemented.

**Context budget warning:** L3 content is expensive. Don't fetch more than 3-5 objects at L3 in a single conversation unless necessary. Use L1/L2 to narrow down first.

### Cross-Cutting Analysis (No tier — standalone)

**Tools:** `solutions-intelligence.search_bundles`, `solutions-intelligence.get_app_overview`, `solutions-intelligence.list_orphans`, `solutions-intelligence_get_security_audit`

| Tool | Use When |
|------|----------|
| `solutions-intelligence.search_bundles` | "Show me CRUD sets, wizard patterns, batch processes" — detected implementation patterns |
| `solutions-intelligence.get_app_overview` | "What are the application layers?" — layer breakdown, central records, most connected objects |
| `solutions-intelligence.list_orphans` | "What's unused?" — unreachable objects by type |
| `solutions-intelligence_get_security_audit` | "Any security issues?" — missing security groups, overly permissive access |

These are application-wide analyses. Call them when the question is about the whole app, not a specific object.

## Navigation Recipes

### "How does feature X work?"
```
L0: solutions-intelligence.get_app_overview → find the cluster for feature X
L1: solutions-intelligence.get_bundle → see all objects in the feature
L3: solutions-intelligence.get_object_code → read the key 2-3 objects
```
**Budget:** 3-5 calls

### "What breaks if I change object X?"
```
L2: solutions-intelligence.get_transitive_dependencies → blast radius, affected clusters
L2: solutions-intelligence_get_entry_points_for_object → which features are affected
```
**Budget:** 2 calls

### "Show me the data model for evaluations"
```
L2: solutions-intelligence.get_app_schema → all record types, fields, relationships
```
**Budget:** 1 call

### "What does object X do?"
```
L3: solutions-intelligence.get_object_detail → content + deps + metadata + impact in one call
```
**Budget:** 1 call

### "Find objects related to scoring"
```
L1: solutions-intelligence.search_objects → search by keyword across name, description, tags
```
**Budget:** 1 call

### "How is the app structured?"
```
L0: solutions-intelligence.get_app_overview → overview
Cross: solutions-intelligence.get_app_overview → layers, central records, connectivity
```
**Budget:** 2 calls

### "What patterns exist in the app?"
```
Cross: solutions-intelligence.search_bundles → CRUD sets, wizards, batch processes, utilities
```
**Budget:** 1 call

### "Is object X unused?"
```
L2: solutions-intelligence.get_dependencies → check if anything calls it
Cross: solutions-intelligence.list_orphans → or check the full dead code report
```

### "Show me dependents for all security groups"
```
L1: solutions-intelligence_get_objects_by_type(objectType: "group") → get all group names
L2: solutions-intelligence.get_dependencies(objectNames: "Group1,Group2,Group3,...") → all dependents in one call
```
**Budget:** 1 call

### "I need to create a new object similar to X"
```
L1: solutions-intelligence.search_objects → find similar objects
L3: solutions-intelligence_get_object_xml → get the XML template to base the new object on
```
**Budget:** 2 calls

## Integration with Existing Workflows

### Knowledge Query Workflow
When the knowledge-query-workflow activates and the target application has a `app_name`:
- **Phase 0 (new):** Check KB first before live API calls
- For Technical/Business/Structural questions → use KB L0-L3 navigation
- For Impact questions → `solutions-intelligence.get_transitive_dependencies` replaces recursive `solutions-intelligence.get_dependencies` calls
- For Data Model questions → `solutions-intelligence.get_app_schema` replaces multiple Record Type fetches
- For Inventory questions → `solutions-intelligence_get_objects_by_type` replaces paginated `lcp-api.listApplications`
- Fall back to live API only when KB doesn't have the answer (recently created objects, current values)

### Design Document Workflow
When the design-doc-workflow activates and the target application has a `app_name`:
- **Step 3 Track A:** Replace Atlas with KB navigation
  - `solutions-intelligence.get_app_overview` → understand application shape
  - `solutions-intelligence.search_objects` → find relevant objects (replaces Atlas search_objects)
  - `solutions-intelligence.get_bundle` → understand feature context (replaces Atlas get_bundle)
  - `solutions-intelligence.get_object_code` → read SAIL code (replaces Atlas get_object)
  - `solutions-intelligence.search_bundles` → find similar implementation patterns (replaces Atlas search_bundles)
- **Step 3.5:** `solutions-intelligence.get_transitive_dependencies` can supplement live `solutions-intelligence.get_dependencies` for risk assessment
- **Step 3 Track B (live API):** Still needed for recently created objects and database verification

### Code Review Workflow
When the code-review-workflow activates and the target application has a `app_name`:
- **Pre-analysis (new):** Before reviewing individual objects, use KB to understand context:
  - `solutions-intelligence.get_bundle` → understand the feature being modified
  - `solutions-intelligence.get_dependencies` → understand what each object connects to
  - `solutions-intelligence.get_transitive_dependencies` → pre-compute blast radius for modified objects
- **Step 4 (object review):** Still uses live API for source code + diff (KB may be stale)
- KB provides the "why" context that makes review findings more actionable

### Spike Research Workflow
When investigating a topic and the target application has a `app_name`:
- Use KB as the primary codebase research tool
- `solutions-intelligence.get_app_overview` → understand application layers
- `solutions-intelligence.search_bundles` → find existing implementation patterns to reference
- `solutions-intelligence.get_app_schema` → understand data relationships
- `solutions-intelligence.search_objects` → find relevant objects by keyword
