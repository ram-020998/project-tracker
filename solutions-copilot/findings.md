## 1. buildwithclaude (John Rogers)

**Source:** https://gitlab.appian-stratus.com/john.rogers/buildwithclaude
**Purpose:** Standalone MCP server connecting Claude Code to Appian environments via LCP Plugin APIs

### Architecture

```
Claude Code → (stdio/MCP) → lcp_mcp_server (Python) → (HTTP Basic Auth) → Appian /suite/webapi/lcp-api
```

### Key Files

| File | Purpose |
|------|---------|
| `setup.sh` | One-command bootstrap: installs deps, creates .env, syncs creds, symlinks skills |
| `.mcp.json` | Project-scoped MCP servers (appian + appian-docs) |
| `.claude/settings.json` | Hooks, telemetry, permissions, plugins |
| `.claude/settings.local.json` | Credentials (generated by sync script, gitignored) |
| `.claude/agents/` | Domain-specific review agents (sail-null-guard, sail-button) |
| `.kiro/steering/appian-dev.md` | Same guidance adapted for Kiro |
| `skills/appian-*/SKILL.md` | 13 curated skills (record types, SAIL, interfaces, etc.) |
| `scripts/sync_env_to_settings.py` | .env → .claude/settings.local.json credential sync |
| `scripts/hook_post_edit.py` | Auto-syncs when .env edited inside Claude |
| `scripts/hook_pretooluse_appian.py` | Agent review gate (blocks unsafe SAIL patterns) |
| `src/lcp_mcp_server/` | The MCP server (150+ tools) |
| `verify` | Credential smoke test |
| `claude-appian` | Convenience launcher (re-syncs then exec's claude) |

### How the MCP Server Runs

- Runs locally as a Python subprocess spawned by Claude Code via stdio
- Uses `uv run --directory . python -m lcp_mcp_server` (no Docker)
- Server inherits environment variables from Claude Code session (credentials come from settings.local.json)
- Dependencies managed by `uv` + `pyproject.toml` + `uv.lock`

### Credential Flow

```
.env (user edits) → sync_env_to_settings.py → .claude/settings.local.json → Claude Code env → MCP server inherits
```

### Hook System (3 hooks)

1. **PreToolUse** (`hook_pretooluse_appian.py`): Inspects SAIL expressions for patterns (ri! without null guards, invalid button styles). Blocks call and forces specialist sub-agent review before retry.
2. **PostToolUse** (`hook_post_edit.py`): When .env is edited, auto-runs credential sync.
3. The agents (`sail-null-guard.md`, `sail-button.md`) are input transformers, not conversational — they receive tool_input JSON, validate/fix, return corrected version.

### Skills Structure

```
skills/appian-<topic>/
├── SKILL.md          # YAML frontmatter (name, description) + content
└── references/       # Optional detailed docs (component catalogs, patterns)
```

Skills are symlinked to `~/.claude/skills/` by setup.sh. Claude loads them on demand based on description matching.

### Telemetry

- Honeycomb (OpenTelemetry) for operational observability
- LangSmith (via Claude Code plugin) for LLM-quality tracing
- Both configured in settings.json — no user setup required

### Key Patterns to Adopt

- Manifest-driven setup with symlinks to global config
- PostToolUse hook for credential sync
- Skills as shared reference docs loadable by any agent
- PreToolUse hooks as quality gates
- Verify script to confirm environment health
- Dual-platform support (.claude/ + .kiro/)

## 2. lcp-api / a!migo (Saurabh Sabat)

**Source:** https://gitlab.appian-stratus.com/saurabh.sabat/lcp-api
**Purpose:** Python library wrapping Appian LCP Plugin APIs for Kiro IDE/CLI usage

### Architecture

```
Kiro IDE/CLI → (Python calls) → appian_lcp client → (HTTP Basic Auth + JWT) → Appian /suite/webapi/lcp-api
```

### Key Differences from buildwithclaude

| Aspect | buildwithclaude | lcp-api |
|--------|----------------|---------|
| Interface | MCP server (stdio) | Python library (direct calls) |
| Auth | Basic Auth + Browser SSO | Basic Auth + JWT (beta API) |
| Multi-env | Single .env | Multi-profile via profiles.yaml |
| API coverage | 150+ MCP tools | 130 plugin + 107 beta = 237 ops |
| SDK generation | Pre-generated, committed | `make generate` from spec |
| Workflows | Skills (passive docs) | Active Python (data model, bulk rename) |
| Testing | Minimal | 200 unit + live integration tests |
| Target | Claude Code (primary) | Kiro IDE/CLI (primary) |

### Profile System

```yaml
default: dev
api: beta
profiles:
  dev:
    url: https://your-dev-site.appiancloud.com/suite
    username: your-username
    password: your-password
    app_uuid: your-app-uuid
    site_id: 1234567
  staging:
    url: https://staging-site.appiancloud.com/suite
    # ...
```

Supports per-profile `api` override (plugin vs beta), `app_uuid` scoping, passwords in OS keychain.

### Ops Dispatch Module

`src/appian_lcp/ops/` — the layer Kiro calls. Handles:
- Profile resolution
- app_uuid injection
- Pagination
- Error formatting
- Auto-discovery of available operations

### Workflows

1. **Data Model from Google Sheet:** Parse sheet → validate → generate SQL (MariaDB + Oracle + PostgreSQL) → create record types + fields + relationships. Idempotent.
2. **Bulk Rename:** Discover objects → plan rename (collision detection) → execute sequentially → report.

### JWT Authentication (Beta API)

- Requires VPN + cluster access to get site's private key
- Tokens cached at `.jwt-cache/<profile>.jwt` (3-hour expiry)
- Kiro generates tokens automatically using `site_id`

### Key Features to Leverage

- Multi-profile environment switching (this IS our environment registry)
- 237 operations already implemented and tested
- Google Sheets → data model workflow
- Bulk rename workflow
- Known issues tracker (`docs/known-issues.yaml`) queryable at runtime
- Capture system ("say capture that" for structured failure logging)

## 3. Appian LCP Plugin Architecture

### The Stack (Bottom to Top)

1. **Appian Platform** — applications, record types, process models, interfaces, etc.
2. **Java Plugin** (`com.appian.research.lcpapis_2.0.0.jar`) — registers expression functions that use internal Appian Java services
3. **Appian Application** (`Core LCP API Staging Site.zip`) — 14 Web APIs that bridge HTTP → plugin functions
4. **Python Clients** (buildwithclaude MCP / lcp-api library) — consumer interfaces

### Two Plugins

| | Plugin 1: lcpapis | Plugin 2: composer-rest-api |
|---|---|---|
| **Type** | Expression functions + Web API wrapper | Native REST plugin |
| **Path** | `/suite/webapi/lcp-api` | `/suite/lcp/api` → `/a/composer` |
| **Auth** | HTTP Basic Auth (via Web API) | JWT |
| **Coverage** | 150+ operations (core) | Limited (Personas, newer features) |
| **Needs zip app?** | Yes | No |
| **In configs as** | `base_url` / `api: plugin` | `beta_base_url` / `api: beta` |

### How Requests Flow

```
Client → POST /suite/webapi/lcp-api/record-types (Basic Auth)
       → Appian Web API authenticates
       → Calls fn!doPost(toJson(http!request))
       → Plugin parses path, calls RecordTypeDefinitionService
       → Returns JSON response
```

The `/lcp-api` endpoint is a **catch-all** — the plugin handles all routing internally. Older specific endpoints (`/content`, `/applications`, `/design-objects`) still work but are legacy.

### Prerequisites for a Target Appian Site

1. Appian version 26.2+ (cloud)
2. Java plugin JAR deployed
3. Appian application (zip) imported (creates Web APIs)
4. Feature flags enabled:
   ```
   appian.feature.ae.dev-copilot-api.lcp-api-plugin=true
   conf.mcp.enabled=true
   appian.feature.ae.lcp-enabling-team.record-type-apis=true
   # ... per-feature flags
   ```

### OpenAPI Specs Available

- `lcp-api-via-plugin.openapi.yaml` — main plugin API
- `lcp-beta.openapi.yaml` — beta API
- `lcp-alpha.openapi.yaml` — alpha/experimental

## 4. Live Plane — Current State (Somasundaram)

**Purpose:** Custom Appian application deployed to environments, exposing Web APIs for AI agent consumption.

### Three Responsibilities (Current)

1. **Application Knowledge** — app tree, object content, dependencies, clusters, patterns, architecture, semantic search, staleness
2. **Object CRUD** — create constants, get/update objects (overlaps with LCP API)
3. **Deployment** — create packages, deploy, check results (overlaps with Deployment MCP)

### Unique Capabilities (Not in LCP API)

- Semantic search on live data
- Cluster/pattern detection
- Architecture overview generation
- Staleness tracking (knows what's changed since last parse)
- Entry points for objects
- Shared objects across apps

### Limitations

- Must be deployed to every environment
- We maintain it (bug fixes, version upgrades)
- Different environments may run different versions
- Limited to what we expose via custom Web APIs
- 42 tools total

### Decision for Solutions Copilot

Strip the Live Plane to **read-only knowledge** for the Live Plane. Remove:
- Object creation (→ lcp-api handles)
- Object modification (→ lcp-api handles)
- Package creation/deployment (→ Deployment MCP handles)
- SAIL evaluation (→ lcp-api handles)
- SQL queries (→ lcp-api handles)

## 9. Kiro Global Configuration

### Directory Structure (`~/.kiro/`)

```
~/.kiro/
├── agents/           ← Agent configs
├── powers/
│   ├── installed/    ← Power folders (POWER.md + steering/)
│   ├── installed.json← Registry of installed powers
│   └── registry.json ← Available powers from marketplace
├── skills/           ← Skill folders
├── settings/
│   └── mcp.json      ← Global MCP server configuration
├── steering/         ← Global steering files
├── extensions/       ← Kiro extensions
└── sessions/         ← Session history
```

### Power Structure

```
~/.kiro/powers/installed/<name>/
├── POWER.md          ← Activation trigger + description
├── mcp.json          ← MCP servers (REMOVING in refactor)
└── steering/         ← Specialized instructions
```

### installed.json Format

```json
{
  "version": "1.0.0",
  "installedPowers": [
    { "name": "live-plane", "registryId": "user-added" },
    { "name": "sql-forge", "registryId": "user-added" }
  ]
}
```

### MCP Config Format (`~/.kiro/settings/mcp.json`)

Powers register their MCP servers under `powers.mcpServers`:
```json
{
  "mcpServers": { /* global servers */ },
  "powers": {
    "mcpServers": {
      "power-<name>-<server>": { /* config */ }
    }
  }
}
```

## 10. Key Architectural Decisions

| Decision | Rationale |
|----------|-----------|
| Intelligence Server is read-only | Clear separation: reads ≠ writes ≠ deploys |
| Use lcp-api for writes (not rebuild) | 237 ops already maintained by Saurabh |
| Use Deployment MCP for deploys | Open source, maintained, purpose-built |
| Strip Live Plane to knowledge-only | Remove overlap with lcp-api and Deployment MCP |
| Powers don't bundle mcp.json | MCP is infrastructure, not power-scoped |
| setup.sh bootstraps everything | One command, idempotent, profiles supported |
| Platform agnostic design | Same knowledge works for Kiro, Claude Code, Gemini |
| Declarative manifest | Single source of truth for what's installable |

## 11. Reference: buildwithclaude Setup Script Behavior

```bash
# Preflight checks
python3 >= 3.11, uv installed

# Step 1: Create .env from .env.example
# Step 2: Install dependencies (uv sync)
# Step 3: Sync .env + OS username into .claude/settings.local.json
# Step 4: Symlink skills into ~/.claude/skills/
# Step 5: Warn if .env still has placeholders
```

Key properties:
- Idempotent (safe to re-run)
- Detects browser auth mode and installs Playwright extra
- PostToolUse hook auto-syncs on .env edits inside Claude
- `./claude-appian` wrapper re-syncs on every launch
- `./verify` tests credentials and re-syncs on success
